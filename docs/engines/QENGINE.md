**Engine id:** `qengine` · **Slug prefix:** `qengine/` · **Status:** two two-card slugs: the 27B ⚠️ Production w/ caveats, Flash-Next 🐣 Incubating; copies of both for three cards (`multi3`, QEngine's tuned setup) and four (`multi4`), not booted on the two-card reference rig: the 27B ones 🧪 Experimental, the Flash-Next ones 🐣 Incubating · **Requires:** NVIDIA RTX 3090s (sm_86, the card QEngine is tuned for), ideally three; a driver with CUDA 13.1 support. ## What it is

[QEngine](https://github.com/bpx03/QEngine) (Krzysztof Jagus) is an independent C++/CUDA inference engine (`libqengine.so`, about 26k lines) with its own Python server. It is built for one model on one kind of machine: **Qwen3.8-27B INT4** (RedHatAI's compressed-tensors W4A16 checkpoint and its MTP head) on **three RTX 3090s** with tensor parallel 3 over PCIe. It isn't a fork of any engine we ship, so its lineage class is `new` ([ADDING_ENGINES.md](../ADDING_ENGINES.md)).

What it does, from its README:
- **INT4 weights**, repacked at load into tensor-core layouts, with an INT4 GEMV for decode and an INT4 GEMM for prefill.
- **Tensor parallel over PCIe**, with the all-reduces inside the kernels. It uses GPU-to-GPU P2P when the driver grants it, and otherwise a slower path through host memory.
- **MTP speculative decoding**, with 1–7 drafts a step chosen from the measured acceptance. The author also publishes an MTP head fine-tuned on the engine's own answers (`model_mtp_ft.safetensors`, a release asset). It adds **lookup drafts** from the token history.
- **FP8 (e4m3) K / V** in a shared pool per GPU, up to 262,144 tokens a conversation, with prefix and KV reuse and a host-RAM archive of evicted conversations.
- **Continuous batching** of up to 32 sequences, structured output (llguidance), tool calls, and thinking on or off with reasoning-effort levels.
- **OpenAI- and Anthropic-compatible APIs** (`/v1/chat/completions`, `/v1/models`, `/v1/messages`) on port 8080, `/health`, and a dashboard with Prometheus metrics on port 9393.

**Cards:** three are the tuned configuration. The author has measured two (72–85% of the three-card throughput, full 262K context, `QE_MAX_SEQS=32`). One card is experimental: it starts only with `QE_MAX_SEQS` 1–4, for about 85K–112K tokens of context.

**Models:** Qwen3.8-27B, RedHatAI's INT4 only. It reads `weight_packed` / `weight_scale` (compressed-tensors `pack-quantized`), so other INT4 checkpoints don't load, including our AutoRound one (`auto_gptq` packing: `qweight` / `qzeros` / `scales`). That one has the same scheme (int4, symmetric, group 128, the same layers) but a different file layout and different rounding. Its 1.3 release adds a second engine for **Qwen3.8-Flash-Next** (`libqflash.so`), which reads only the author's own INT4 layout ([bpx03/Qwen3.8-Flash-Next-QEngine](https://huggingface.co/bpx03/Qwen3.8-Flash-Next-QEngine), converted from Intel's AutoRound checkpoint). Upstream calls it a preview: tested on one machine, no quality benchmark yet. 1.3-rc4 fixes that engine's INT8 MoE prefill kernel, which now and then gave a few tokens wrong activations, mostly on two GPUs.

## Image

The author publishes `ghcr.io/bpx03/qengine` in two forms per release: `:<release>`, text only (about 0.3 GB), and `:<release>-vision`, which adds PyTorch for the vision encoder (about 3 GB to pull). Each image's `org.opencontainers.image.revision` label names its source commit. The profile pins **`1.3.5.9-vision`** by digest (`sha256:e670c0d9…`, source `ee98bd10` = git tag `v1.3.5.9`), upstream's stable release: `latest` and `vision` moved to it, and it contains 1.3.5.8. The rollback is 1.3.5.7-vision (`sha256:2d790174…`), the previous stable pin and the last under the PolyForm Noncommercial licence, or 1.3.5.6-vision (`sha256:12692990…`), and the launchers inject the pin as `QENGINE_IMAGE`. Its server, engine libraries and entrypoint are byte-identical to the text image's, so text serving is the same in either; the vision image is what lets the slugs take images.

**1.3.3.1** (pinned 2026-11-01, a fix-only release for both engines) fixes replies that could pick up text from another conversation running at the same time: when a new request was admitted between two chunks of another prompt's prefill, the next generation step of a running request ran on the new request's sequence slot, so it continued that conversation and sent the tokens to the wrong client (or ended early with empty content). Only a server handling several requests at once is affected, which both slugs allow (several slots); upstream recommends that everyone upgrade. Flash-Next also had the same mix-up after a failed prompt in a batched prefill. Both engines now refuse a generation step on a slot that is still prefilling or no longer in use, and log a `BUG:` line if one is attempted.

**1.3.4.1** (released 2026-11-02 and pinned with 1.3.4.2 the same day) fixes Flash-Next's CUDA graphs running out of VRAM under agent load (the 1.3.4 known issue, seen in #1846's 8-pack gate). The cached graphs of an agent load need about 300 MB a card and had grown into the 256 MB margin the expert cache leaves free; the engine now keeps its own room for them, `FLASH_GRAPH_MB` (256 MB a card, half of it out of that margin), frees the least recently used graphs to stay inside it, and builds a prompt-shaped graph only when that shape came back within the last 64 prompt steps (`FLASH_PFGRAPH_WINDOW`). Upstream's cost: about 0.8% fewer expert groups on the GPU, decode within 1%. `/api/stats` gains a `graphs` block per card. The Flash-Next slug forwards both settings. A steering vector that can't be loaded no longer stops the server (our composes set none). 1.3.4.1 also ships **new default Flash-Next weights**: the DeltaNet projections in INT8 and the shared expert and n-gram projections calibrated with GPTQ, the routed experts unchanged. Upstream measured next-token KL against the BF16 model at 0.119 against 0.267 (top-1 agreement 89.1% against 83.3%, on jyohukuchan's public reference set), for about 4% slower single-stream decode and 5% with 8 conversations, prefill unchanged, and a 129 GB download. The Flash-Next slug runs these weights (the model profile pins their revision, `c0022018`); QEngine 1.3.4 and older stop at load on them, so the engine pin and the weights move together. The earlier files stay on the Hub as revision `v1.3.4`. Upstream's club-3090 8-pack with them: 117.0 / 124.7 of 150 (thinking off / on, 3 runs), against 114.7 / 128.7 with the earlier files; the run ranges overlap. The 27B engine is unchanged.

**1.3.4.2** (pinned 2026-11-02) makes Flash-Next decode faster and changes neither weights nor the 27B (its output is bit for bit 1.3.4.1's). Upstream on three cards, against 1.3.4.1 on the same day: single-stream decode +7.5% narrative and +9% code, decode at 10K / 90K depth +12%, 8 agents at once 897 → 1,022 tok/s (+14%), prefill +1 to +3%; on two cards, 359 tok/s with 8 agents. That wins back the new weights' decode cost. One conversation's output is bit for bit 1.3.4.1's; with several at once the attention partial results merge in another order, so tokens can differ in rare places (KL to BF16 unchanged). The changes: batched-decode attention splits its keys by length instead of always 8 ways (`FLASH_ATTN_DMIN`, 16; the Flash-Next slug forwards it), the small all-reduces and all-gathers of a decode step go card to card over P2P, and the attention queries cross as fp16. The dashboard's agents table and `qetop`, broken since 1.3.4, work again, and both show the running version and build (`/api/stats` `version`, `build`; its `history` counters moved to `history_drops`). Its three other new settings, `QE_AR_SPLIT`, `QE_AG_LL` and `FLASH_QX16_DEC`, are off switches for debugging (upstream's `docs/advanced.md`), so like QEngine's other debugging settings the composes don't forward them. Booted on both slugs on the reference rig (2026-11-02): verify-full passes with vision 4/4 on each, Flash-Next on the new weights (MTP acceptance length 3.97; host RAM at ready 87.4 GiB, inside the slug's 88).

**1.3.4.3** (pinned 2026-11-03) adds the thinking budget per reasoning effort (below; [bpx03/QEngine#4](https://github.com/bpx03/QEngine/issues/4)) and fixes the two Flash-Next issues we filed: an idle server no longer keeps CPU cores busy ([#5](https://github.com/bpx03/QEngine/issues/5)), and after the load the engine drops the page cache of the weight files, so they no longer push a disk-mode n-gram table out of RAM ([#6](https://github.com/bpx03/QEngine/issues/6)). Requests' efforts: `max` now renders as `xhigh` and `minimal` as `low` (both were `medium`); other unknown efforts still render as `medium`. Speed, outputs and weights are 1.3.4.2's. Its three new settings, `FLASH_WEIGHTS_COLD`, `FLASH_TP_SPIN_US` and `FLASH_NGRAM_SPIN_MS`, are switches back to the old behaviour in upstream's `docs/advanced.md` and aren't forwarded. A malformed `QE_THINKING_BUDGET` now stops the server at start-up (1.3.4.2 warned and ran without a budget). Booted 2026-11-03 on both slugs: verify-full all pass, vision 4/4, MTP acceptance length 3.97 (Flash-Next) and 6.22 (27B). With tiny budgets set through our knobs (64 / 128 / 256), each effort's reasoning stopped 26–31 tokens past its budget (QEngine's wrap-up sentence), a request's own `thinking_budget` won, `max` took the `xhigh` entry, and `/api/stats` counted `effort:low`, `effort:medium`, `effort:xhigh` and `request`. With `THINKING_BUDGETS=off` the start-up line says off and the same requests reasoned past those budgets (`budget_from`: `none`).

**1.3.5.7** (pinned 2026-11-10) is upstream's new stable release (`latest` and `vision` moved to it from 1.3.5.6). - **27B: two image prompts prefilling at once each keep their own image rows.** Up to two prompts prefill at the same time, and one image table held only the newest prompt's rows, so the first could embed the second one's image. In upstream's test that overlaps two image prompts, the first one's logits now match the run alone (before: up to 0.44 apart). Not reproduced here.
- **`--lsa` without manual steps (27B).** A bare `--lsa`, or `QE_LSA=auto` (the 27B compose forwards it), downloads the released index map on the first start (6.3 MB, from Prefrontal AI's latent-sparse-attention release `d-lsa-weights-v1`, Apache-2.0), checks its sha256, converts it in plain Python and caches it in `~/.cache/qengine/lsa`, the engine cache. Offline, or with `QE_FETCH_ASSETS=0` and nothing cached, the server starts with full attention and logs `LSA: off: …`. It is lossy and opt-in, and only one long conversation at a time uses it. ### Disk cache: `KV_OFFLOAD_DISK=1`

Both slugs can keep their conversations on disk across restarts, with QEngine's own `--disk-cache`: the 27B since #1941, Flash-Next from 1.3.5.3 (below). It's off by default. The 27B first:

- **Turning it on:** `KV_OFFLOAD_DISK=1`, the same setting as the vLLM and SGLang disk tiers.
  - **Where:** the files go in `qengine-qwen3.8-27b/` under `KV_OFFLOAD_DIR` (else `<data dir>/kv-offload`, `~/.local/share/club-3090/kv-offload`).
  - **The cap:** `KV_OFFLOAD_DISK_GB` caps it, in GiB in total; unset, QEngine's own 200 GiB applies. QEngine removes the oldest files to stay under it and keeps no free-space margin, so size it to the volume.
  - **No `KV_OFFLOAD_GB` needed:** unlike vLLM and SGLang, it's a tier under QEngine's own host-RAM archive (`QE_KV_ARCHIVE_GB`, on by default).
- **What gets saved:** a conversation's KV and state, written in the background whenever it leaves VRAM, after 120 s idle (`--persist-idle`), and at shutdown.
  - **Speed:** a 48K-token conversation is a 2.5 GB file, written in 1.8 s.
  - **Safety:** each file is written as `.tmp` and renamed, and its fingerprint (model files, cards, KV split, per-card sizes) is checked on load, so a file from another setup is ignored.
- **What it reuses:** a returning conversation is copied back instead of recomputed.
  - **A new conversation with the same system prompt** starts from the checkpoint at that prompt's end, while a saved conversation still holds that checkpoint.
  - **The limit (1.3.4.3):** a conversation that itself came from the cache was saved with its own end only. Once it replaced the original, the system-prompt checkpoint was gone from disk. 1.3.5 keeps it ([bpx03/QEngine#14](https://github.com/bpx03/QEngine/issues/14), fixed upstream; not re-measured here).
  - **Not any shared prefix:** Qwen3.8's DeltaNet state exists only at those checkpoints.

Measured on the reference rig (2026-11-04, QEngine 1.3.4.3, `KV_OFFLOAD_DISK_GB=20`), a 48K-token system prompt, temperature 0:

| Request | Disk cache | Reused | Time to first token |
|---|---|---|---|
| first conversation (cold) | on | 0 | 18.1 s |
| after `docker restart`: same system prompt, new question | on | 48,168 | 0.33 s |
| after `docker restart`: the first conversation continued | on | 48,229 | 0.22 s |
| after `switch.sh` recreated the container: that conversation continued again | on | 48,281 | 0.30 s |
| after `docker restart`: same system prompt, new question | off (control) | 0 | 20.2 s |

verify-full passed on the disk-cache boot. The folder is made group-writable at start, so you can delete its files without root.

**Flash-Next, from 1.3.5.3 (in upstream's stable from 1.3.5.6):** the same setting turns on Flash-Next's own disk cache ([bpx03/QEngine#15](https://github.com/bpx03/QEngine/issues/15)), in `qengine-qwen3.8-flash-next/`. Its code isn't the 27B's:
- **What gets saved:** a conversation of 2,048 tokens or more, in the background, when it leaves VRAM (at most once a minute per conversation), after 120 s idle and at shutdown. Each file is rewritten whole.
- **What it reuses:** a continued conversation is read back whole. A new one with the same system prompt reads only the part up to that prompt's end. Reads run in the background, and after 30 s a prompt gives up on its file and prefills.
- **Checks:** every read is checksummed, and a file serves only the same build, weights (path, size and date), cards, layout and YaRN factor. An upgrade starts empty, and a damaged file is removed and prefilled.
- **Limits:** it keeps 1 GB of the disk free. A failing disk costs only the cache, with a log line.
- **Shutdown:** the slug's `stop_grace_period` is 120 s for the shutdown save, as upstream asks for `docker stop`.
- **Side effect:** QEngine also keeps its start-up link and decode calibration (`comm_probe_*.txt`, `comm_decode_*.txt`) in that folder, so the first start with it on measures again, for a few seconds.

Measured on the reference rig (2026-11-07, QEngine 1.3.5.3, `KV_OFFLOAD_DISK_GB=20`, two 3090s at 230 W), a system prompt of 100,933 tokens, temperature 0, every answer correct:

| Request | Disk cache | Reused | Time to first token |
|---|---|---|---|
| first conversation (cold) | on | 0 | 28.5 s |
| after `docker restart`: same system prompt, new question | on | 100,902 (1.57 GB read in 0.97 s) | 1.41 s |
| after a second `docker restart`: the first conversation continued, alone | on | 100,943 (2.37 GB read in 1.44 s) | 1.84 s |
| after `docker restart`: same system prompt, new question | off (control) | 0 | 28.0 s |

The shutdown saves took 2.3–13.1 s (2.37 GB for the first conversation). After the run the folder held 5.6 GiB in three conversations. The folder is made group-writable at start, and the test files were deleted without root.

The Flash-Next slug stays 🐣 Incubating. The 27B slug was booted and benched on 2026-10-28 on two 3090s at 230 W: 147.2 / 216.3 tok/s decode (narrative / code), 2,430 prefill @10K and 1,786 @90K, MTP acceptance length 3.4, 23.4 GB a card, verify-full 8 + 2 n/a ([BENCHMARKS.md](../../BENCHMARKS.md)). The Flash-Next slug was booted and benched the same day: 164.0 / 170.6 tok/s decode, 1,921 prefill @10K and 2,373 @90K, MTP acceptance length 2.8, 24.1 GB a card, host RAM 88 GB at ready (up to ~114 GB as the archive fills), verify-full 8 + 2 n/a. Benched again on 2026-11-02 on 1.3.4.2 with the new default weights, at the slug's 8 slots with vision on: 165.5 / 158.4 decode, 1,879 prefill @10K and 3,615 @90K, MTP acceptance length 2.9, 23.9 GB a card, host RAM 93.5 GB at ready (the header's figure is 94 from that date).

Community PR #1836 (eddietheengineer) validated both slugs on another two-card rig and found two Flash-Next problems there: a NaN on a ~76K-token prefill with `FLASH_COMM=auto`, and an out-of-memory in the 8-pack's agent pack at 8 slots. Its fixes are `FLASH_COMM=ce` and `FLASH_MAX_SEQS=4`. Neither reproduced on the reference rig: 90K and 107K needles on `auto`, which picked the P2P path here, and 8 concurrent multi-turn conversations to 27.7K tokens at the default 16 slots. So the defaults stay, and the compose header names both settings. With both, an 8-pack run there later aborted on a CUDA-graph out-of-memory (#1846): QEngine logs `graph instantiate out of memory, other graphs dropped` first, then a failed allocation (`flash_seq.cu:298`) ends the engine. `FLASH_EC_MARGIN_MB=1024`, the VRAM a card keeps free beside the expert cache (256 MB by default), fixed it there, for about 10% of decode and 5–7% of prefill. The first line also appears on the reference rig, in 3 of 6 boots and at the default 16 slots too, never followed by a crash so far. The default stays QEngine's: the abort is the engine's to fix. QEngine 1.3.1 drops its cached graphs and retries instead of aborting, and 1.3.2 fixes the root cause (the sampling kernel of batched requests needed more GPU stack than a CUDA context reserves); neither has been re-run on that rig. With `FLASH_COMM=ce`, 1.3.2 also turns on a copy-engine prefill pipeline that has a fault of its own: on two CMP 170HX (#1841, unpatched 1.3.2 too) a concurrent request whose prompt shared a prefix with another slot came back with 0 tokens, and on that rig's patched build both cards twice hung. `FLASH_QSA_PIPE_CE=0` turns the pipeline off (5 of 5 sweeps clean there, about 4% prefill at 90K); the Flash-Next compose forwards it. It reproduces on the reference rig too (2026-10-31): with `FLASH_COMM=ce`, one stream of `concurrency-probe.sh --sweep`'s 8K × 4 cell came back with 0 tokens, and with `FLASH_QSA_PIPE_CE=0` the same sweep was clean. `FLASH_COMM=auto` keeps P2P here (P2P tax 1.79, under the 1.90 cap for one NUMA node), so the default doesn't run the pipeline. **QEngine 1.3.3 fixes it** (pinned 2026-11-01): the pipeline numbered a very short batch piece (1–8 rows, such as a resumed conversation) as if no exchange were pending, so two pieces read each other's data. On the reference rig the same `FLASH_COMM=ce` sweep with the pipeline on ran 9 of 9 cells clean on 1.3.3 (no `gen 0`, no collective timeout, no restart), so `FLASH_QSA_PIPE_CE=0` is no longer needed; it stays forwarded as an off switch. 1.3.3 also keeps 2 MB per GB of host memory registered after load (the archive and pinned prefixes) out of the expert cache, 112 MB a card at our defaults, which had come out of the 256 MB `FLASH_EC_MARGIN_MB`; on a CUDA-graph out-of-memory it drops the least recently used half of its cached graphs before the rest, with a 64 MB emergency reserve a card (`FLASH_OOM_RESERVE_MB`).

On the 27B, the engine is faster with its two release assets (`token_rank.bin`, `model_mtp_ft.safetensors`, unchanged since v1.0; upstream: ~8-9% more accepted drafts). `setup.sh` doesn't fetch them, and the compose header and the weights entry give the `gh release download` line for the weights folder. From 1.3.2 the server downloads the missing ones itself at start (0.85 GB, checked against the release's `SHA256SUMS`) into the engine cache, which is kept per image, so each new pin downloads them again; in the weights folder they're found first.

The composes give the container only the two chosen cards (`device_ids`, so `launch.sh --gpus` picks them) and set `QE_GPUS=0,1`, the cards as the container numbers them. QEngine's own entrypoint overrides `CUDA_VISIBLE_DEVICES` with `QE_GPUS` (default `0,1,2`), so a forwarded mask would not reach it. The engine cache (`~/.cache/qengine`: the GEMM tune table, stats, logs and the one-engine-per-GPU locks) is mounted from the engine cache directory, so the GEMMs are tuned once per image.

**On cards smaller than 24 GB.** The two two-card composes declare `Requires-min-vram-gb: 24`, the card size their slot counts were set for (32 on the 27B, 8 on Flash-Next), so `switch.sh --list` hides them on smaller cards. A launch by name still works, and on two or more cards preflight only warns. The four three- and four-card composes declare 16, from one community run at their own slot counts (32 on the 27B, 16 on Flash-Next) on 4 × RTX 5080 16 GB ([#1999](https://github.com/noonghunna/club-3090/issues/1999): QEngine 1.3.5.7, `VISION=0`, the slug shapes run as services of their own, not the composes):
- all four started at 262K, with tensor parallel chosen on both card counts;
- verify-full, verify-stress and the soak passed on three of them; Flash-Next on three cards ran speed and concurrency only;
- what 16 GB cards give up is KV pool. Flash-Next's came out at one 262K window shared by its 16 slots, on both card counts. The 27B's came out at 3.0 windows on four cards and 1.6 on three, for 32 slots. A conversation larger than what is left of the pool ends early;
- Flash-Next on three 16 GB cards keeps 36.6 GB of expert groups in host RAM, about 88 GB pinned with the n-gram table, above its slug's 75 GB estimate for 24 GB cards.

Vision was off in those runs, and every QEngine compose defaults to `VISION=1`. On the 27B the encoder sits on the last card and takes from the pool there: 25.4% of it at the three-card slug's shape (414,720 to 309,248 tokens, 1.18 windows, so one 262K conversation fits and a second of that size doesn't; verify-full vision 4/4, [#1999](https://github.com/noonghunna/club-3090/issues/1999#issuecomment-6803496714)), and 16.8% on four cards at 8 seats on 1.3.4.3 ([#1953](https://github.com/noonghunna/club-3090/issues/1953)). Flash-Next keeps the encoder's blocks in host RAM: at its four-card slug's shape the pool stayed at 262,144 with vision on (verify-full vision 4/4, [#1998](https://github.com/noonghunna/club-3090/pull/1998#issuecomment-6795743305)).

QEngine itself starts on smaller cards, fitting fewer slots or a smaller context at start. Upstream measured:
- the 27B on 3 × 8 GB and 2 × 12 GB;
- Flash-Next on 3 × 8 GB, and on 2 × 8 GB at a 65K context.

@Hazelhof also ran both models on those cards at 8 slots on the 27B and 6 on Flash-Next ([#1966](https://github.com/noonghunna/club-3090/issues/1966)). For a two-card slug on cards under 24 GB, or any slug on cards under 16 GB, launch by name and lower `QE_MAX_SEQS` or `FLASH_MAX_SEQS`.

## Thinking and effort

Our knobs reach QEngine through its server flags (in `QE_EXTRA_ARGS`) or its own variables:

| Knob | QEngine | |
|---|---|---|
| `ENABLE_THINKING` | `--think 1` / `0` | the default for requests that set none; `true` unless set |
| `SPEC_N` | `--mtp-k <n>` | the most MTP drafts a step (the engine adapts below it); 0 turns MTP off, lookup drafts stay on |
| `REASONING_EFFORT` | `QE_REASONING_EFFORT` | `low` unless set; `low`, `medium` or `xhigh` |

QEngine serves its own copy of the Qwen3.8 chat template (`server/templates/qwen38_syssafe.jinja`), whose default effort is `xhigh`. From 1.3.1 its server takes a default for requests that send none, `QE_REASONING_EFFORT` (or `--reasoning-effort`; #1842), on chat completions, messages and count_tokens alike, and the compose sets it from `REASONING_EFFORT`. It refuses to start on an image whose `server/app.py` doesn't read that variable, so an older image can't quietly go back to `xhigh`. Until 2026-10-30 the compose copied the template at boot with its one `reasoning_effort|default('xhigh')` replaced, and served the copy with `--template`. A request's own effort still goes to QEngine's template, which maps `high` and (from 1.3.4.3) `max` to `xhigh` and `minimal` to `low`, as our patched template on the vLLM and SGLang slugs does. From 1.3.5.5 `none` turns thinking off, like `enable_thinking: false`, wherever an effort can come from (`reasoning_effort`, `chat_template_kwargs`, `reasoning: {"effort": "none"}`, Anthropic `output_config.effort`); before, it rendered as `medium` with thinking on ([#1966](https://github.com/noonghunna/club-3090/issues/1966)). Any other effort outside the three still renders as `medium`.

**Thinking budget (from 1.3.4).** A request can cap its thinking: OpenAI `thinking_budget` (top level or in `chat_template_kwargs`; `thinking_token_budget`, `max_thinking_tokens` and `reasoning.max_tokens` work too) or Anthropic `thinking: {"type": "enabled", "budget_tokens": N}`. At the budget the server adds a one-sentence wrap-up and `</think>`, and the model answers as usual. `QE_THINKING_BUDGET` sets it for requests that send none: one number (from 1.3.4), or from 1.3.4.3 a budget per effort, `low:N,medium:N,xhigh:N`. When `max_tokens` would run out inside `<think>`, the server closes the thinking early enough to leave room for the answer (`QE_THINK_TAIL`, on by default), and a non-streamed reply that ends with no text and no tool call is sampled again up to twice (`QE_EMPTY_RETRY`). From 1.3.4.3 both slugs set it from our effort map, as the vLLM and SGLang slugs do: `THINKING_BUDGET_LOW` / `_MEDIUM` / `_XHIGH` (unset = 4096 / 16384 / 32768) become `QE_THINKING_BUDGET=low:4096,medium:16384,xhigh:32768` (`scripts/lib/effort_budget.py`, one `[effort-budget] v1` readback line in the boot log), `THINKING_BUDGETS=off` sets none, and a `QE_THINKING_BUDGET` set by hand wins. QEngine picks the entry from the effort the prompt is rendered with, so a request that names no effort gets the `low` entry (`REASONING_EFFORT` defaults to low); a request's own budget always wins. The composes refuse an image older than 1.3.4.3, which would ignore the map. `scripts/probe-effort-budget.sh <url>` checks it live, as on the vLLM and SGLang slugs (boot with `THINKING_BUDGET_LOW=64 _MEDIUM=128 _XHIGH=256` for the default mode; `--expect-off` and `--positive` for the controls). Its slack allows QEngine's wrap-up sentence (26–31 tokens over the budget on 1.3.4.3); `/v1/messages` reports no reasoning tokens, so those two cases read which source set the budget from `/api/stats` (inside the container), and QEngine serves no Responses API. The early close and the retry change output only for replies that would otherwise end inside their thinking or come back empty, but that is what some 8-pack scenarios score: quality results from 1.3.4 on aren't strictly comparable with earlier versions'.

## What's wired

- the engine profile (`scripts/lib/profiles/engines/qengine.yml`);
- engine kind `qengine` in `scripts/lib/engine-kind.sh`, from its id, its profile `type`, a `qengine-` container name, its image and `/v1/models` `owned_by: "qengine"` (it sends no `system_fingerprint`);
- container discovery (`qengine-` in the prefix set; port 8080 counts with that evidence);
- the `QENGINE_IMAGE` arm in both launchers;
- the label in `health.sh`, the Genesis skip in `verify-full.sh`, and the kind in `report.sh`, `run_context.py` and the local registration types;
- the two slugs, their weights variants and the launch knobs above, including the 27B's disk cache (`KV_OFFLOAD_DISK`, `KV_OFFLOAD_DISK_GB`).

QEngine prints `[stats]` lines for log parsers, in llama.cpp's timing format and vLLM's `SpecDecoding metrics` format, so `bench.sh`'s engine-side timings and acceptance capture and `verify-full.sh`'s MTP acceptance check read it with no QEngine-specific code (checked on the 27B slug, 2026-10-28).

QEngine reports neither its slot count nor its context over HTTP, so `served-slots.sh` (the concurrency step), `verify-stress.sh` and `concurrency_probe.py` read them from its boot log, when the container can be read (#1850). A host-run QEngine (`CONTAINER=none`) is recognised by `/v1/models`' `owned_by`. `verify-stress.sh` doesn't apply its absolute VRAM-margin check to QEngine, as it doesn't to Strata: QEngine allocates its KV pool (and, on Flash-Next, its expert cache) at load, so free VRAM is set at start and doesn't move with the context (763 → 763 MB across a 120K ladder on the 27B, 3 → 3 MB across 240K on Flash-Next, 2026-10-29). It prints the ladder's drop instead (#1826).

`health.sh` has a QEngine section: slots and context from the boot log, the latest `[chat]` requests, decode rates, MTP + lookup acceptance and, on Flash-Next, the expert cache's hit rate. `bench.sh`'s interconnect block reads QEngine's own transport lines (it links no NCCL): the 27B's `P2P: decode all-reduce GPU to GPU` or its host-memory path, Flash-Next's `no peer access` line, and both slugs' `[comm] prefill transfers`. From 1.3.5 both say which path decode took (`[comm] decode collectives …`, chosen by `QE_DECODE_COMM`), and that line wins: the 27B still prints the GPU-to-GPU line when peer access opens, also when decode then goes through host memory. c3 classifies a `qengine-` container as QEngine, not as llama.cpp from its 8080 port, and matches a rebench REPORT.md's container line to it.

The composes don't publish QEngine's metrics port: the dashboard has no auth and a write endpoint (`POST /api/reset`). `QE_METRICS_PORT=<port>` opts in. The compose passes it to QEngine, which then listens on that port, and `switch.sh` (so `launch.sh` and c3 too) adds an override at launch that publishes it on the host's loopback only, `127.0.0.1:<port>`. Compose can't publish a port conditionally, hence the override (`scripts/lib/qengine_metrics.py`); a compose you run with `docker compose` yourself gets no mapping. Set it for one launch (`QE_METRICS_PORT=9393 bash scripts/switch.sh --force <slug>`) or for every QEngine slug (`bash scripts/settings.sh set QE_METRICS_PORT=9393`); `switch.sh` refuses a value that isn't a port before it stops what is running. Two QEngine slugs running at once need two ports. Unpublished doesn't mean unreachable: inside the container the port is bound to 0.0.0.0, so the host can still reach it on the container's bridge address, as before. From another machine, use an SSH tunnel (`ssh -L 9393:127.0.0.1:9393 <rig>`).

- the gateway's native `/v1/messages` passthrough. QEngine serves `/v1/messages` and `/v1/messages/count_tokens` itself, but the passthrough admits only `owned_by` vllm / sglang, so LiteLLM translates instead.
